# 需求录入

你的职责：把需求方的口语化描述，规范化成 `.claude/backlog.md` 里的标准条目。**只录入，不实施。**

**输入：** $ARGUMENTS

**前置检查：** 若 `.claude/backlog.md` 不存在，提示需求方先跑 `/task:init` 初始化，然后结束。不要自己凭空创建。

---

## Step 1: 解析需求

从描述中提取每一条独立需求。若一句话里包含多个可独立交付的诉求，**拆成多条任务** —— 例如「加个知识库页面，顺便把上传大小限制改了」是 2 条。

拆分判据：能否独立提交、独立验证。不能独立的不拆（例如「加端点」和「加端点的测试」是 1 条）。

## Step 2: 补齐字段

读 `.claude/backlog.md` 底部的「ID 分配规则」拿到下一个可用 ID。

| 字段 | 怎么定 |
|------|--------|
| ID | 从「下一个可用 ID」取，递增。录完必须回写更新该行 |
| 任务 | 一句话，动宾结构，说清「改什么达到什么效果」。不要写成"优化 XX"这种无验收点的表述 |
| 模块 | 优先沿用待办池 / 进度流水里已出现过的模块名；项目若有模块索引文档（如 `current-sprint.md`、`module-spec-registry.md`）则对照它选；确实是新模块则新起名并在备注里标注 |
| 状态 | 默认 `待开始`；若识别出前置未满足则 `阻塞` |
| 依赖 | 填任务 ID（`T-0xx`）或人工事项编号（`H-0xx`）；无则填 `—` |
| 备注 | 需求方的原始诉求要点、相关文件路径；**以「验收：…」开头写一条可用命令或操作判定的完成标准**（需求方给了就照抄，没给就按描述拟一条并标「（AI 拟，可改）」）。自动循环的 worker 以它作为完成判据。P2 / P3 任务再判一条 `验收方式：自动`（见下） |

**验收方式：自动**（只给 P2 / P3；交付后机器验收全过就免人工确认，见 `${CLAUDE_PLUGIN_ROOT}/skills/loop/VERIFY.md` §2）。同时满足才写，写了就标「（AI 判定，可改）」，任何一条拿不准就不写（默认要人确认，最多等超时默认通过）：
- 验收标准完全能用测试 / 命令的输出判定，不需要人看效果；
- 没有用户能感知的变化：不改 UI、CLI 输出文案、对外 API 的请求 / 响应、给人看的文档；
- 不落在高风险领域（schema / 迁移、认证 / 加密、计费 / 配额、删数据、部署配置、依赖）。

典型：补测试、修不稳定用例、内部重构（行为不变、有测试覆盖）、清理死代码。需求方明说「这个要我看」的，不写。

## Step 3: 判定优先级

按 `backlog.md` 的优先级定义判定。判定时**看后果，不看需求方的语气** —— "很急"不等于 P0。

| 判据 | 级别 |
|------|------|
| 已在线上产生错误数据 / 安全漏洞 / 服务不可用 | P0 |
| 用户能感知的功能缺失、报错、体验断点 | P1 |
| 功能增强、重构、补测试、清技术债 | P2 |
| 没有明确使用场景的想法 | P3 |

**判定不确定时，问需求方**，不要自己拍。特别是 P0/P1 边界 —— 误判 P0 会打断正在进行的任务。

## Step 4: 写入并回执

1. 追加到 `backlog.md` 对应优先级的表格末尾（若该表只有「暂无」占位行，替换掉它）。
2. 更新底部「下一个可用 ID」。
3. 若新任务是 P0 且当前有「进行中」任务，在回执里明确提示需求方：是否打断当前任务。

回执格式（简洁，不要复述表格全文）：

```
已录入 2 条：
- T-009 [P1/计费] 修复配额并发扣减导致的超额
- T-010 [P2/测试] 补 quota_service 并发场景测试（依赖 T-009）

待办池：P0×0 P1×2 P2×5 P3×2
```

---

## 边界

- **不实施。** 即使需求只需改一行，也只录入。需求方会用 `/task:next` 驱动实施。
- **不重排已有任务的优先级。** 除非需求方明确要求。
- **录入前查重。** 若待办池里已有语义重复的条目，不新建，而是补充到已有条目的备注里并告知需求方。
- **手写条目要容错。** 需求方可能直接手编 `backlog.md`，格式不规范（缺 ID、缺模块）。你在下次操作该文件时顺手补齐，不要报错。
